## 流程图


```text
Stage 0: V-Droid baseline
  - 复现原始 V-Droid
  - 记录失败类型、SR、latency

Stage 1: Raw trajectory collection
  - goal
  - history
  - before_ui
  - action_space
  - selected_action
  - after_ui
  - final success/failure

Stage 2: Critic-label annotation
  teacher / 人工标注下面每个 transition
  - outcome
  - failure_type
  - suggested_recovery
  - summary_to_history

Stage 3: Critic distillation
  - 蒸馏训练 C: 
    before_ui + action + after_ui + goal + history -> 
critic JSON:
{
  - outcome
  - failure_type
  - suggested_recovery
  - summary_to_history
}

Stage 4: Critic-history generation
  - 用 C 给更多 raw trajectories 自动生成 critic JSON
  

Stage 5: P3 data construction for verifier
  - 构造的chosen/rejected prompt 中包含critic产生的summary_to_history
  - 让 V 学会读 critic feedback

Stage 6: Verifier LoRA tuning
  - 微调 V-Droid verifier
  - 避免看到 failure 就总是 back

Stage 7: Joint inference
  - V 选动作
  - 执行
  - C 写 critic json
  - 下一步 V 读了C的反馈summary_to_history + goal + history + current UI再选动作
```

这里history是原论文就有的：只是总结这一步action做了什么，做到什么地步
而我们新增的critic产生的summary_to_history，包含outcome/failure_type/suggested_recovery的隐含信息，是总结上一步对整个goal的作用，总结这个action该不该做，做得如何

---

## Critic 蒸馏时应该学什么？

critic 不应该只学：

```text
progress / failure / done
```

它还应该学一个给 verifier 使用的短 summary：

```text
summary_to_history
```

所以 critic 的蒸馏目标最好是：

```json
{
  "outcome": "progress | failure | done | no_effect",
  "failure_type": "none | wrong_page | wrong_target | text_error | popup_blocking | premature_complete | no_effect",
  "suggested_recovery": "continue | navigate_back | clear_text | close_dialog | retry | complete_task",
  "summary_to_history": "The previous action opened the wrong folder. Avoid continuing there and go back to the file list."
}
```

其中最重要的是最后一个字段：

```text
summary_to_history
```

因为它会被写入下一步 history，让 verifier 看。

---
## Stage 3 和 Stage 4 的区别

 
“既然 critic 蒸馏时已经学 summary，那 Stage 3 用 critic 生成 summary 是不是重复？”

不重复，区别是：
蒸馏阶段

```text
让 C 学会怎么生成 summary
```

这是训练 critic。
批量生成阶段

```text
用训练好的 C 给大量轨迹自动补 summary
```

这是为了构造 verifier 的训练数据。

也就是说：

```text
Stage 3: train C to be a summary writer
Stage 4: use C as a summary writer
```

---
## 意义

不是简单的：

```text
先蒸馏 critic，再微调 verifier
```

而是：

```text
先蒸馏一个能够生成 verifier-readable feedback 的 critic，
再用这种 feedback 构造 verifier 的 critic-augmented P3 数据，
最后微调 verifier 学会利用 critic feedback。
```

一句话：

> **critic 蒸馏时就要学习 summary，因为 critic 的核心角色不是只判断对错，而是把 post-action outcome 压缩成下一步 verifier 能读懂的 history memory。**

## Stage 2: Critic-label annotation 轨迹数据集标注

```json
{
  //原始轨迹
  "task_id": "MarkorTranscribeReceipt",
  "goal": "Create a file in Markor, called receipt.md with the transactions from the receipt.png. Use Simple Gallery to view the receipt. Please enter transactions in csv format including the header \"Date, Item, Amount\".",
  "step_id": 0,
  "history": [],
  "before_ui_html": "",
  "after_ui_html": "",
  "action_space": [],
  "scores": [],
  "selected_action": "",
  "human_label": "",
  "summary": "",
  "screenshot": "",
  "screenshot_ann": "",
  
  
  //需要让人工+AI标注得到的
  "outcome": "progress",
  "failure_type": "none",
  "suggested_recovery": "continue",
  "summary_to_history": "The previous action opened the wrong folder. Avoid continuing there and go back to the file list."
}
```


该prompt 可以同时用于 **当前数据集标注**。核心是：让 C 判断“已执行动作的后果”，但可以参考 `action_space` 判断是不是当时有更合理选择。

```text
You are a post-action critic for a mobile GUI agent.

Your task is to evaluate the executed action at the current step.

Given:

- task_id: the task name
    
- goal: the user's instruction
    
- step_id: the current step index
    
- history: previous action summaries before this step
    
- before_ui_html: UI state before the executed action
    
- after_ui_html: UI state after the executed action
    
- action_space: available candidate actions before execution
    
- selected_action: the action that was actually executed
    
- screenshot / screenshot_ann: optional visual evidence of the UI state
    
- summary: the original action summary, if available
    

Judge whether the selected_action helped complete the goal by comparing before_ui_html and after_ui_html, while using goal, history, and action_space as context.

Output only a valid JSON object with the following fields:

{  
"outcome": "progress | failure | done | no_effect",  
"failure_type": "none | wrong_page | wrong_target | text_error | popup_blocking | premature_complete | no_effect",  
"suggested_recovery": "continue | navigate_back | clear_text | close_dialog | retry | complete_task",  
"summary_to_history": "..."  
}

Labeling rules:

1. outcome
    

- progress: the action moves the agent closer to completing the goal.
    
- failure: the action moves the agent away from the goal, selects the wrong target, opens the wrong page, enters wrong text, or causes an incorrect state.
    
- done: the goal is fully completed after this action.
    
- no_effect: the action causes no meaningful UI or task-state change.
    

2. failure_type
    

- none: use this when outcome is progress or done.
    
- wrong_page: the action opens the wrong app, page, folder, screen, or menu.
    
- wrong_target: the action selects the wrong file, contact, button, item, checkbox, or object.
    
- text_error: the action enters incorrect, incomplete, or wrongly formatted text.
    
- popup_blocking: a popup, dialog, permission request, keyboard, or overlay blocks progress.
    
- premature_complete: the agent stops or marks the task complete before the goal is actually finished.
    
- no_effect: the action has no useful effect.
    

3. suggested_recovery
    

- continue: use when the current state is useful and the agent should keep going.
    
- navigate_back: use when the agent should return from a wrong page, folder, or screen.
    
- clear_text: use when incorrect text should be removed and re-entered.
    
- close_dialog: use when a popup or dialog should be closed or handled.
    
- retry: use when the action had no effect or another action should be tried from the current UI.
    
- complete_task: use only when the goal is fully completed.
    

4. summary_to_history  
    Write one concise sentence starting with "[Critic]".  
    It should summarize the effect of the previous action for the next verifier step.  
    It should mention whether the action progressed, failed, had no effect, or completed the task.  
    If the action failed, briefly state what should be avoided or recovered.  
    Do not include long reasoning.  
    Do not mention irrelevant UI details.  
    Do not output markdown.  
    Output JSON only.

```

## Stage 3: Critic distillation 构造蒸馏 C 的数据集

蒸馏训练时的prompt和上面的长prompt不同，改为短版

蒸馏训练C的input：
```text
You are a post-action critic for a mobile GUI agent.

Given task_id, goal, step_id, history, before_ui_html, action_space, selected_action, after_ui_html, summary, and screenshot_ann, evaluate the effect of the selected action.

Output only valid JSON with four fields: outcome, failure_type, suggested_recovery, summary_to_history.

Allowed outcome: progress, failure, done, no_effect.
Allowed failure_type: none, wrong_page, wrong_target, text_error, popup_blocking, premature_complete, no_effect.
Allowed suggested_recovery: continue, navigate_back, clear_text, close_dialog, retry, complete_task.
summary_to_history must be one concise sentence starting with "[Critic]" and written for the next verifier step.

Input:

task_id:
{task_id}

goal:
{goal}

step_id:
{step_id}

history:
{history}

before_ui_html:
{before_ui_html}

action_space:
{action_space}

selected_action:
{selected_action}

after_ui_html:
{after_ui_html}

summary:
{summary}

screenshot_ann:
{screenshot_ann}

Now evaluate the selected_action based on the input above.

Return JSON only.
```

注意这里没有score，不要让C过度依赖score来做判断。

蒸馏训练C的output label（前面让AI标注后的）

```json
{
  "outcome": "",
  "failure_type": "",
  "suggested_recovery": "",
  "summary_to_history": ""
}
```
